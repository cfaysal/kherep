# Codex original-owner receive and processing receipts

Fetch is an offer, not a processing acknowledgement (#711). This contract applies to Codex original-owner prompt and CLI intake. Claude delivery, task-runner settlement, original-owner resume, reply/send behavior, privacy gates and wire states retain their existing contracts.

1. Run `kherep-node msg inbox --from <recorded-owner-id> --receive` when a hint arrives. Plain inbox listing remains read-only. The bounded batch returns only complete framed bodies and a persisted opaque receipt outside peer framing. Receipt metadata binds exact IDs, current owner/address and offer generations; it contains no body copy.
2. Process the returned messages under the standing peer-content rules. The Maestro runs the printed `kherep-node msg inbox --ack <receipt> --from <owner-id>` itself after processing. The user performs no manual ACK. If tool/transport output was truncated, do not ACK.
3. ACK conditionally changes only matching offered records to existing `delivered` state under record locks. Wrong owner, changed generation/address, refused or never-offered records fail closed. An identical repeated ACK is idempotent. A later turn can complete an earlier offer; no invented native turn ID is needed.
4. ACK output reports the local commit separately from Worker persistence. The existing exchange retries delivered status until its persistence receipt arrives. Neither a local commit nor Worker persistence proves the sender has received its receipt; sender status must be read at the sender for that claim. Stop does not acknowledge fetched content, and no extra processed-then-Stop phase is required.

Repeated explicit receive immediately recovers interrupted and legacy offered records without incrementing offers or exhausting refusal retries. ACK complete batches before requesting the next batch so recovered oldest offers do not crowd out later IDs. Hook and batch output stay within 6 KiB. When the next record does not fit whole, output names `kherep-node msg inbox --from <owner-id> --receive <messageId>` and issues no ACK-capable receipt for incomplete content. This exact single receive accepts only a currently owned accepted/offered record, validates the existing protocol text limit (16,384 characters), and uses the existing 128 KiB descriptor/output safety bound. It emits the entire framed body or no offer receipt. It cannot combine with history, ACK or diagnostic `--message-id`/`--expect-*` selectors. A complete single receive returns the ordinary processing receipt. The diagnostic exact-inbox authored-parent/tuple/hash checks are unchanged.

With native Queue opt-in, one durable owner reservation precedes turn-budget consumption and native submission. The original batch IDs, input and count remain immutable; later IDs remain accepted and unattempted. An uncertain enqueue, incomplete attempt history, partial Queue listing or unconfirmed cleanup blocks another native group. CP hints remain independent. Restart reconstructs reservations from existing outstanding attempts; malformed history never authorizes enqueue or deletion. Exact existing Queue ID/input matching and complete absence readback retire the reservation. The next poll may notify remaining accepted IDs; IDs already received and ACKed need no extra card. Per-ID attempts remain durable. This changes batching across distinct groups; it does not assert that same-ID duplicate enqueue was observed.

## Synthetic acceptance

From the source checkout:

```powershell
node --test --test-concurrency=1 modules/control-plane/node/codex-intercom-acceptance.test.mts modules/control-plane/node/codex-inbox-ack.test.mts modules/control-plane/node/codex-native-pending.test.mts modules/control-plane/node/codex-native-reconcile.test.mts modules/control-plane/node/codex-queue-producer.test.mts
```

The harness creates synthetic node and Codex homes in a temporary directory, starts the real CLI/hook source as child processes, checks interrupt recovery and Stop, performs the synthetic Maestro's explicit processing declaration, and exercises existing NodeClient status retry, persistence receipts and sender `sent/` updates. Worker frames and Queue clients are explicit test doubles; there is no network, model execution, actual installed-home read, original-owner resume or live installation. Native fixture tests separately cover immutable pending groups, concurrent reservations, daemon restart, uncertain enqueue and exact cleanup/readback gates. Source tests do not establish Desktop activation or real model compliance. Those require separately authorized target acceptance.
